# PWA & App Shell

[← Back to README](../README.md)

**What this covers:** what makes this app installable, what the service worker
caches and what it refuses to cache, how to rebrand the icons, and why the
worker is written by hand instead of generated by a plugin.

A progressive web app is an ordinary website with three extra pieces: a
**manifest** describing its name and icons, a **service worker** — a script the
browser keeps running alongside your pages, which can answer network requests —
and a set of icons. Together they let a browser offer "Install", give the
installed app its own window with no address bar, and show something useful when
the network is gone.

All three ship with this repo and are already wired up. There is nothing to
enable and no environment variable to set. The service worker registers itself
in production builds only, so `pnpm dev` behaves like a plain website.

## Do you need to do anything?

Only two things, and neither is urgent:

- **Rebrand the icons and manifest** before you ship, or your app installs under
  the placeholder name and mark. See [Icons](#icons) below.
- **Understand the caching rules** before you add caching of your own. This is
  an authenticated app, and the service worker's strictness is a security
  property, not a performance tuning choice.

## Try it locally

The service worker is skipped in development on purpose — a stale worker
caching your own edits is a miserable way to spend an afternoon. To see the real
thing, run a production build:

```bash
pnpm build && pnpm start
```

Then open Chrome DevTools → **Application**. Under **Manifest** you should see
the app name and icons; under **Service Workers** you should see `/sw.js`
activated and running. A Lighthouse "Installable" audit checks the same things
in one pass. In a supported browser an "Install this app" prompt also appears at
the bottom of the page.

To see the offline behaviour, tick **Offline** in DevTools' Network panel and
navigate. You get the `/offline` page rather than the browser's error page.

## What the service worker caches

A service worker sits between your pages and the network and can answer a
request from a cache instead. That is exactly as dangerous as it sounds in an
app where pages are personalised: a cache is shared by everyone who uses that
browser profile, so caching one user's dashboard HTML would hand it to the next
person who signs in on that device.

So the rules are deliberately narrow. Only immutable, impersonal assets are
cached. Everything else goes to the network every time.

| Request                                 | Strategy                                                       |
| --------------------------------------- | -------------------------------------------------------------- |
| `/_next/static/*`, icons, fonts, images | **cache-first** (immutable, fingerprinted)                     |
| Page navigations                        | **network-only**, falling back to `/offline` when disconnected |
| `/api/*`, `/api/auth/*`                 | **never cached** — always network                              |
| Non-GET requests                        | passed straight through                                        |

Cross-origin requests are ignored entirely — the worker only handles same-origin
GETs.

To throw away every cached asset on the next deploy, bump `CACHE_VERSION` in
`public/sw.js`. The activate handler deletes every cache whose name does not
match the current version.

## Registration and updates

Getting a _new_ service worker onto a device that already has an old one is the
part that usually goes wrong, so it is worth knowing what this repo does.

- The worker registers **in production only**
  (`src/components/pwa/service-worker-register.tsx`).
- It registers with `updateViaCache: 'none'`, and `next.config.ts` serves
  `/sw.js` with `Cache-Control: no-cache, no-store, must-revalidate`. Between
  them, the browser always revalidates the worker script itself, so a new
  version is never hidden behind a cached copy of the old one.
- When a new worker finishes installing while an old one still controls the
  page, the page posts it `SKIP_WAITING`, the new worker activates, and the page
  reloads once.
- That reload is guarded: it only fires when a controller was already present
  when the page loaded. On a first visit the worker's initial claim is not
  treated as an update, so a brand-new visitor is not bounced by a reload — and
  an in-flight navigation such as sign-out is not raced by one.

## Icons

Placeholder icons are generated from a single inline SVG into
`public/icon-192.png`, `public/icon-512.png`,
`public/icon-maskable-512.png`, the Next.js favicon and the apple-touch icon:

```bash
pnpm gen:icons
```

To rebrand, edit the SVG mark and colors in `scripts/generate-icons.mjs` — or
drop in real source art — and re-run it. Then update the name, colors and
shortcuts in `src/app/manifest.ts` to match.

## App shell

Protected routes render inside a minimal, borderless shell
(`src/components/shell/`):

- **Desktop:** fixed sidebar plus sticky topbar.
- **Mobile:** the sidebar collapses to an off-canvas drawer — the hamburger
  toggles it, and it closes on navigation or a backdrop tap.
- **Installed PWA:** `env(safe-area-inset-*)` padding keeps the topbar and
  drawer clear of the notch. The root layout sets `viewportFit: 'cover'`, which
  lets content extend under the notch in the first place.
- **Navigation** is data-driven from `src/lib/shell/nav.ts` — add a
  `{ title, href, icon }` entry and it appears, with active-state highlighting.

Public pages (`/`, `/login`, `/register`) keep their own centered layout.

## Why the service worker is hand-rolled

The usual way to add a service worker to Next.js is a plugin — `next-pwa`,
Serwist and friends — which generates the worker at build time from a config
file. This repo does not use one, and the reason is a hard constraint rather
than a preference.

**Turbopack is used for both `dev` and `build`.** The generator plugins hook
into Webpack's build pipeline. Adopting one would mean giving up Turbopack for
the whole app to gain a file that, for this app's needs, is about 130 lines.
That trade is not worth making, so `public/sw.js` is written by hand, ships as a
static file, and needs no build step at all.

There is a second benefit that turned out to matter more than the first. A
generated worker's default recipes are tuned for content sites: precache the
build manifest, serve navigations stale-while-revalidate, cache API GETs.
Applied unchanged to an authenticated app, those defaults leak data between
users on a shared device. Writing the fetch handler by hand means the rules are
readable in one screen, and the comment at the top of `public/sw.js` states the
security constraint the file exists to satisfy. The safest cache is the one you
had to opt into deliberately.

The trade-off is real: no automatic precache manifest, no revision hashing, and
no offline support for pages beyond the single `/offline` fallback. For an app
whose useful pages all require a network round-trip to the database anyway, that
costs nothing.

## Push notifications

The same service worker is what receives push messages, so Web Push builds
directly on this page's machinery: `public/sw.js` handles `push` (showing the
notification) and `notificationclick` (focusing or opening the right tab). It
stays fully inert until the `VAPID_*` variables are set. Setup, sending, and the
design behind it are in [Web Push](push.md).

## Troubleshooting

**No service worker in DevTools.** You are running `pnpm dev`. Registration is
production-only; use `pnpm build && pnpm start`.

**Old assets after a deploy.** Bump `CACHE_VERSION` in `public/sw.js`, then
reload twice — once to install the new worker, once for it to take control. In
DevTools, **Application → Service Workers → Unregister** gives you a clean slate
while developing.

**No install prompt.** The prompt only renders when the browser fires
`beforeinstallprompt`, which it does not do if the app is already installed, or
if the manifest or icons fail an installability check — Lighthouse will name
which. iOS Safari never fires the event at all; there the user installs through
**Share → Add to Home Screen**, and nothing is shown by design.

**The offline page never appears.** It is only a fallback for _navigations_ that
fail. A page that loads and then fires a failing API call shows that call's own
error, not the offline page.
